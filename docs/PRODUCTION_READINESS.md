# برنامه آماده‌سازی تولید جانان (بدون تغییرات زیرساخت سرور)

مبنای ممیزی: شاخه \`main\`، کامیت \`c61d08aec3afc129fad5ff7bf9e1799b9fdbc99b\`.

این سند، برنامه اجرایی پروژه است؛ به معنی اعلام آمادگی کامل Production نیست. تنظیمات VPS، Nginx، PHP-FPM، Redis/Meilisearch روی سرور، CDN، مانیتورینگ سرور و بکاپ زیرساختی عمداً خارج از دامنه این مرحله‌اند.

## اصول معماری

- یک Laravel monolith، یک MySQL و مرزهای روشن بین کاتالوگ، سفارش، انبار و مالی.
- برای ۵۰۰۰ محصول، معماری جداگانه یا میکروسرویس لازم نیست. اول Query، ایندکس و صفحه‌بندی درست؛ ابزار جدید فقط بر اساس اندازه‌گیری واقعی.
- هیچ انتخاب‌گر مدیریتی نباید همه محصولات یا تنوع‌ها را به HTML منتقل کند.
- قیمت، موجودی و سابقه گردش باید از منبع واحد و سرویس‌های دامنه تغییر کنند؛ مقدار موجودی مستقیماً از فرم‌های عمومی نوشته نشود.
- Migration و Import باید قابل تکرار، قابل حسابرسی و دارای گزارش خطا باشند.
- اطلاعات خام واردشده از ERP نباید بدون تطبیق انسانی، برند یا دسته‌بندی حدسی بسازد.

## ممیزی وضعیت فعلی

### بخش‌هایی که زیرساخت دارند

- محصولات و تنوع‌ها در \`products\` و \`product_variants\`، برند و دسته‌بندی مستقل، رابطه‌های Eloquent و Soft Delete.
- \`InventoryService\` و \`inventory_movements\` برای گردش خرید/فروش/اصلاح/ضایعات/برگشت و قفل‌گذاری ردیف تنوع هنگام تغییر موجودی.
- سبد، سفارش، رزرو/کسر موجودی، پرداخت آنلاین، چک و خرید عمده.
- پک عمده و انتخاب تنوع از طریق endpoint جستجوی Ajax با صفحه‌بندی ۲۰تایی؛ فرم پک کل کاتالوگ را بارگذاری نمی‌کند.
- پایهٔ دفتر کل دوطرفه، حساب‌ها و اسناد، به‌علاوهٔ تراکنش‌های مالی دستی.
- Import مرحله‌ای XLSX/CSV/TXT با پیش‌نمایش، Job، گروه‌بندی محصول، قفل مالکیت اجرا و ثبت وضعیت هر Batch.
- صفحه‌بندی محصولات عمومی و مدیریتی و تست مقیاس MySQL برای ۵۰۰۰ محصول و ۵۰٬۰۰۰ تنوع در CI.

### شکاف‌هایی که باید پیش از بهره‌برداری تجاری بسته شوند

- فایل مهاجرت فعلی ۴٬۱۶۸ ردیف و ۶۲۰ گروه محصول دارد؛ این‌ها به معنی ۴٬۱۶۸ محصول اصلی نیستند. هر کد پایه یک محصول و هر کد کامل \`base*variant\` یک تنوع است.
- فایل فعلی برند و دسته‌بندی قطعی ندارد؛ رنگ از بخش انتهایی نام استخراج می‌شود، اما سایز به‌صورت مستقل از این فایل استخراج نشده است.
- Import فعلی اگر حتی یک تنوع از یک گروه نامعتبر باشد، کل گروه را کنار می‌گذارد. این رفتار محافظه‌کارانه است و نباید بدون تصمیم کسب‌وکار به ورود ناقص تغییر کند.
- Importer فعلی XLS قدیمی را نمی‌خواند؛ فقط XLSX، CSV و TXT. تغییر نام پسوند XLS به XLSX تبدیل واقعی نیست.
- مدل تنوع فعلی قیمت خرید/بهای تمام‌شده ندارد؛ بنابراین سود واقعی هر SKU را نمی‌توان فقط با قیمت فروش محاسبه کرد.
- تأمین‌کننده و فاکتور خرید، صندوق فروش حضوری (POS)، دفتر کامل دریافتنی/پرداختنی و دفتر دارایی ثابت هنوز به‌عنوان جریان‌های کامل کسب‌وکار ساخته نشده‌اند.
- زیرساخت حسابداری دوطرفه موجود است، اما تا زمانی که همه رویدادهای دستی، خرید، فروش حضوری، مرجوعی، دریافت/پرداخت و مانده افتتاحیه به سندهای متوازن و گزارش واحد وصل نشده‌اند، نباید آن را حسابداری کامل و جایگزین قطعی هلو تلقی کرد.
- صفحات عمده باید بین «پک‌های آماده» و «کاتالوگ محصولات» مرز روشن داشته باشند. در این شاخه این تفکیک انجام شده است.

## مراحل اجرا

### فاز ۱ — استانداردسازی کاتالوگ و مهاجرت یک‌باره

1. استخراج داده خام و نگهداری Snapshot تغییرناپذیر فایل اصلی.
2. گزارش تکراری‌ها، کدهای نامعتبر، قیمت خالی/منفی، موجودی منفی، نام پایه متناقض و تنوع‌های بدون والد.
3. حفظ کدها به‌صورت String تا صفرهای ابتدای کد از بین نرود.
4. تهیه جدول تطبیق تأییدشده برای کد/گروه هلو به برند و دسته‌بندی جانان؛ تطبیق صرفاً با نام انجام نشود.
5. تعریف سیاست رسمی برای رنگ و سایز و بررسی مواردی که از نام قابل استخراج قطعی نیستند.
6. اجرای Import آزمایشی، تطبیق تعداد محصول/تنوع، مجموع موجودی و قیمت نمونه‌ها؛ سپس Import نهایی با محصولات جدید غیرفعال.
7. ثبت شناسه منبع و نگاشت خارجی برای اجرای مجدد بدون ساخت رکورد تکراری.

### فاز ۲ — تکمیل چرخه عملیات فروشگاه

1. صندوق فروش حضوری با جستجوی نام/SKU/بارکد، انتخاب تنوع، پرداخت، چاپ رسید، ابطال و مرجوعی.
2. تأمین‌کننده، فاکتور خرید و ردیف‌های خرید در سطح تنوع؛ ثبت بهای خرید و ورود موجودی در یک تراکنش دامنه‌ای.
3. دریافت و پرداخت، صندوق و حساب بانکی، بدهکار/بستانکار مشتری و تأمین‌کننده، سررسیدها و تسویه‌ها.
4. تکمیل دفتر کل، تراز آزمایشی، سود و زیان و گردش حساب؛ هر رویداد باید سند دوطرفه متوازن و کلید idempotency داشته باشد.
5. دارایی ثابت: خرید، محل/مسئول، بهای اولیه، استهلاک، تعمیر و خروج از دارایی.
6. نقش‌های کاربری صندوق‌دار، انباردار، فروشنده و مدیر با مجوزهای حداقلی و Audit trail.

### فاز ۳ — کارایی و UX اپلیکیشن

1. صفحه‌بندی سمت سرور برای همه فهرست‌های نامحدود؛ استفاده از cursor pagination فقط در جایی که ترتیب و UX آن مناسب باشد.
2. جستجوی سروری برای انتخاب محصول/تنوع؛ بارگذاری مرحله‌ای و نگهداری فقط انتخاب‌های فعلی.
3. عدم eager-load کردن همه تنوع‌ها در کارت‌های کاتالوگ؛ نمایش تعداد/بازه قیمت و خواندن تنوع‌ها در صفحه جزئیات.
4. کنترل N+1 در توسعه و تست query count برای فهرست‌های پرتردد.
5. بررسی EXPLAIN برای جستجو و فیلترهای پرتکرار؛ افزودن ایندکس بر اساس Query plan و داده واقعی، نه ایندکس‌گذاری کور.
6. کش فقط برای داده‌های عمومی کم‌تغییر با invalidation صریح؛ داده‌های سفارش، موجودی و مالی از کش ناسازگار خوانده نشوند.
7. پردازش تصویر و نسخه‌های responsive متناسب با نیاز فعلی؛ افزودن پکیج سنگین فقط در صورت نیاز واقعی.

### فاز ۴ — تضمین کیفیت و آمادگی انتشار اپلیکیشن

- تست Feature برای مسیرهای کامل صندوق، خرید، سفارش، پرداخت، مرجوعی، موجودی، چک و حسابداری.
- تست همزمانی برای دو فروش روی آخرین موجودی، ثبت تکراری Callback، اجرای مجدد Import و Job ناموفق.
- تست MySQL واقعی کنار SQLite؛ تست Query count و حجم دادهٔ ۵۰۰۰ محصول/۵۰٬۰۰۰ تنوع.
- تست مجوزها، اعتبارسنجی، خطاهای فرم، وضعیت‌های خالی، صفحه‌بندی و تجربه موبایل.
- تست مهاجرت روی دیتابیس کپی‌شده و تطبیق مانده افتتاحیه قبل از خاموش کردن هلو.
- خروجی CI باید شامل تست، Build فرانت‌اند و بودجه asset باشد.

## معیار خروج از مهاجرت هلو

هلو فقط وقتی از کار روزانه کنار گذاشته شود که:
- تعداد و SKU محصولات/تنوع‌ها تطبیق داده شده باشد؛
- موجودی افتتاحیه هر تنوع و ارزش موجودی تأیید شده باشد؛
- مانده صندوق، بانک، مشتریان، تأمین‌کنندگان و چک‌های باز تطبیق داده شده باشد؛
- خرید، فروش، مرجوعی، دریافت/پرداخت و گزارش‌های مالی در جانان تست عملیاتی شده باشند؛
- کاربران فروشگاه سناریوهای روزانه را بدون رجوع به هلو انجام دهند.

تا آن زمان هلو منبع مرجع و آرشیو قابل رجوع باقی می‌ماند.
